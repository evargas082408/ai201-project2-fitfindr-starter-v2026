# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
Two of the three tools call the model, so this path can fail for reasons my
code doesn't control — a rate-limit retry that runs out, or a reply that comes
back empty. My search is also a plain keyword match with a "half the keywords"
cutoff, so a phrasing like "band t-shirt" can miss listings that say "band tee".
I'd rather allow one miss in five than claim a model-backed path never fails.
Tested with `vintage graphic tee under $30` and the example wardrobe, the
matching query in `scenarios.py`.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
This path never touches the model. The branch is an `if not results:` on a list
that `search_listings` always returns, and the diagnostic re-searches are also
pure Python over a fixed file, so the same query gives the same result every
time. Anything less than 5 of 5 would mean the branch itself is wrong, not
unlucky. "Names what to change" means the message contains at least one of: a
dollar amount to raise the budget to, a size to try, or the words "try other
words" with example keywords. Tested with `designer ballgown size XXS under $5`, the
impossible query in `scenarios.py`.

---

## 3. The searched item is the item every later tool receives

Given a query that matches at least one listing (tested with
`denim jacket under $50` and the example wardrobe), the `id` of
`session["selected_item"]` equals the `id` of `session["search_results"][0]`,
**and** equals the `item_id` that `session["tool_calls"]` records for both the
`suggest_outfit` call and the `create_fit_card` call — in 5 of 5 tries.

(`session["tool_calls"]` is a list the loop appends to right before each tool
runs: `{"tool": name, "item_id": <id of the listing it was handed>}`.)

**Why this target:**
This is all bookkeeping in my own loop — the item is read out of the session,
not re-typed or re-generated by the model — so there's no randomness on this
path and one mismatch in five would be a real bug, not noise. It checks three
ids rather than "the outfit mentions the item", because the model's wording
can't prove which dict it was handed but the recorded id can.


---

## 4. The fit card is postable and not a template

Running `vintage graphic tee under $30` five times with the cache off, at
least 4 of the 5 fit cards (a) contain the selected item's price written as
`$` plus the number (e.g. `$24` or `$24.00`), (b) contain the platform name
(`depop`, `thredUp` or `poshmark`, any capitalisation), and (c) are 80 words or
fewer. Separately, the 5 cards have at least 4 different first sentences.

**Why this target:**
The words are supposed to change between runs, so I'm not checking wording —
I'm checking the three things that make it a usable post (the price, where to
buy it, short enough to post) plus a check that it isn't a template. 4 of 5
rather than 5 of 5 because at temperature 0.9 the model sometimes paraphrases
("under twenty-five bucks") or drops the platform even when the prompt asks for
it, and I'm only controlling that through the prompt.


---

## 5. The query's price and size are parsed and respected

For these five queries, each stating a price and/or size a different way —

1. `vintage graphic tee under $30` → max_price 30
2. `90s track jacket in size M` → size M
3. `platform sneakers size 8` → size 8
4. `denim jacket for less than 50 dollars` → max_price 50
5. `chunky cardigan, size medium, max $40` → size M, max_price 40

— `session["parsed"]` holds exactly the stated `max_price` and `size`, with
`None` for whichever one the query doesn't state, **and**
no listing in `session["search_results"]` costs more than that `max_price` or
fails the size rule in the README's Tool Inventory — in at least 4 of the 5
queries.

**Why this target:**
The filtering itself is deterministic, but the parsing is regex over free text,
and query 4 ("less than 50 dollars", no `$`) and query 5 ("medium" spelled out)
are the phrasings I trust least. A wrong parse is silent — you get results
above your budget and nothing says so — which is why I care about it more than
speed. I'd call it broken at 3 of 5, not unlucky.
